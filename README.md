# TimeAary

使用 **Kotlin + Jetpack Compose** 开发的本地优先 Android 时间与目标管理应用：公历 / 农历纪念日、正倒数日、数值进度、计数、目标 / 习惯、专注、父子任务、待办及统计，统一采用注重可读性与性能的**液态玻璃**界面。

> 项目状态：已开始工程开发，首批包含公历单次正倒数日、待办、Room 分页与四入口界面，并已配置 GitHub Actions。尚未取得云端构建 / 真机验收结果，不是全功能完成版本。实施状态见 [开发记录](docs/DEVELOPMENT.md)。

- 首个正式版本：`1.0.0`，标签 `v1.0.0`；开发版为 `1.0.0-dev` / `1`，正式发布前递增版本码
- 正式发行架构：仅 `arm64-v8a`
- 开源许可：**GPL-3.0-only**，仅 GNU GPL 第 3 版
- 详细清单、页面布局与验收：[项目开发要求](PROJECT_REQUIREMENTS.md)
- 应用图标：[TimeAary_log.png](TimeAary_log.png)，作为统一品牌与桌面启动图标的源素材。

## 1. 范围约定

**本文功能清单全部纳入必做范围**，包括纪念日、进度、计数、习惯、专注、待办、统计、小组件等模块；不包含账号体系与 VIP 商业体系。

- 不做注册、登录、绑定、用户资料、密码找回、账号注销或应用账号云同步。
- 不做 VIP、订阅、支付、激活码、购买恢复、会员校验或任何功能付费墙。
- 所有本地业务功能直接开放，不设置会员权益判断或付费数量限制。
- 保留本地、WebDAV 和第三方网盘备份。第三方存储的授权 / 凭证不等于 TimeAary 账号，用户未配置时核心功能仍可离线使用。
- 关于、公告、反馈和更新使用 TimeAary 自有内容与 GitHub 入口，不接入行为追踪 SDK。
- 开发可以分阶段，但下面的功能基线都是 `1.0.0` 全功能正式版的验收项。确实依赖第三方授权、硬件或系统能力的项目须记录状态和替代路径，不能无声删除。

## 3. 页面结构与液态玻璃 UI

### 信息架构

**手机悬浮底栏：任务 / 待办 / 统计 / 设置**。纪念日属于任务类型，日历在任务和待办页面展开，不额外堆叠底栏入口。

| 页面 | 布局与操作 |
| --- | --- |
| 任务首页 | 顶部日期与工具栏 → 可收起周 / 月历 → 分类 / 类型筛选 → 混合任务列表；侧栏管理分类，悬浮新增打开类型面板 |
| 新建面板 | 父任务、进度、计数、目标 / 习惯、正倒数日、专注；待办页使用自己的快速新增面板 |
| 任务详情 | 类型专属摘要 → 快捷操作 → 趋势 / 热力图 / 月历 → 记录 / 灵感笔记；编辑与更多菜单统一 |
| 父任务详情 | 父目标摘要与聚合进度 → 进行中 / 已完成 / 已暂停分段 → 子任务列表与加入入口 |
| 专注计时 | 中央环形进度与时间，底部开始 / 暂停 / 继续 / 结束；外围提供声音、常亮、悬浮及历史入口 |
| 待办 | 顶部日期与视图切换 → 周 / 月历、列表或四象限 → 未完成 / 已完成及子项 → 快速新增 |
| 统计 | 日 / 周 / 月 / 年分段 → 日期导航 → 摘要及可排序统计模块 → 时间线入口 |
| 设置 | 外观、显示、交互、安全、提醒、组件、备份、帮助与关于分组；不保留账号卡片或 VIP 横幅 |
| 辅助页面 | 分类 / 归档 / 搜索 / 笔记 / 分享 / 权限说明 / 备份配置等，复用统一工具栏与玻璃面板 |

### 应用图标

- 统一使用项目根目录的 [TimeAary_log.png](TimeAary_log.png)，用于桌面启动图标、启动页品牌标识及关于页。
- Android 图标资源须由该源图生成，适配自适应图标、圆形遮罩与不同屏幕密度，保持比例和主体完整，不拉伸、不覆盖源文件。
- 不提供节日 / 科技等其他品牌启动图标切换；任务、分类和工具按钮的内容图标仍独立配置。

### 视觉方向

- 采用“清透水晶 + 冷蓝时间刻度”的视觉方向，背景轻、数据清楚；液态感重点用于悬浮底栏、选中滑块和操作面板，不让每一行都持续流动。
- 统一玻璃卡片、底栏、气泡 / Snackbar、分类抽屉、弹窗、选择器、底部面板与应用内计时条。
- 使用半透明材质、受控背景模糊、边缘高光、细描边与轻量按压变形；图表坐标、输入区和重要提示优先使用稳定底色。
- 普通文字对比度至少 **4.5:1**，大文字及关键非文本控件至少 **3:1**，按最终合成背景测量。
- 底栏适配系统安全区，内容保留底部空间，新增按钮和计时条互不遮挡；平板改为导航栏轨或双栏。
- 提供高 / 标准 / 低效果和高对比度模式，低配设备不做实时模糊，200% 字体与 TalkBack 仍可完整操作。
- 小组件采用静态玻璃质感；系统通知、系统权限弹窗和系统分享面板受 Android 控制，不要求强制玻璃化。

## 4. 技术架构与性能

| 领域 | 规划选型 |
| --- | --- |
| UI / 状态 | Kotlin、Compose、Material 3、ViewModel、StateFlow、Coroutines、单向数据流 |
| 导航 / 注入 | Navigation Compose、Hilt |
| 持久化 | Room、Paging 3、DataStore、kotlinx.serialization |
| 日期 | java.time + 可替换的农历适配层 |
| 提醒 / 计时 | AlarmManager、WorkManager、持久化计时状态机、合规前台服务 |
| 媒体 / 集成 | Media3 音频、Coil、Glance / RemoteViews、Biometric、SAF / MediaStore |
| 远端备份 | 封装的 OkHttp 网络层、WebDAV / 网盘存储适配器 |
| 图表 | Compose 图表适配层，稳定库经性能与许可证验证后锁定；热力图按可见范围绘制 |
| 构建 / 测试 | Gradle Kotlin DSL、Version Catalog、Convention Plugins、JUnit、Room / Compose 测试、Macrobenchmark / Baseline Profiles |
| CI / 发布 | GitHub Actions，标签驱动 GitHub Releases |

- 模块化单体，公共 Task 身份与各类型详情 / 明细分离，不照搬巨型宽表。
- 索引、SQL 聚合、分页、轻量列表投影和增量派生计算，禁止主线程读写和全量常驻内存。
- 图片 / 音频保存在文件层，数据库保存引用；数值使用 BigDecimal 或定点数，不用 Float 作为事实数据。
- 基准覆盖 **10 万任务、30 万提醒配置、100 万操作 / 会话明细**；性能目标为待验证预算，不是已取得成绩。
- 备份使用一致性快照与流式读写；数据库 schema、导出格式与迁移路径全部版本化，禁止破坏性迁移。
- 建议 minSdk 26，最终在初始化时确认；工具链和依赖版本核对兼容矩阵后锁定，禁止动态版本。

## 5. 云端构建与目录约定

- 本地没有 Android 构建环境，不执行本地 Gradle 编译；Kotlin 单元测试、Lint、debug / release 编译均在 GitHub Actions 运行。
- 推送或创建 PR 后自动执行 Android checks，也可手动运行；通过后从 `app-debug` 下载 debug 包，从 `checks` 下载报告和 Room schema。普通 CI 额外进行 unsigned release 压缩编译但不上传 unsigned 包。
- 应用源码与路径使用中性命名，不能嵌入项目名、GitHub 用户名、仓库名或地址；品牌只用于展示资源值，远程入口以后由独立配置注入。
- 不创建 `main` 等目录，实际源码位于 `app/src/code`、资源位于 `app/src/resources`、测试位于 `app/tests`，Manifest 位于 `app/src/AndroidManifest.xml`。
- 单个 `app` 模块按 `model`、`datetime`、`data`、`ui` 划分职责，不创建空 feature 模块；身份暂定 `local.daybook`，minSdk 26。
- CI 独立安装固定 Gradle 并校验分发包 SHA-256，不改动已有 `gradlew` 路径的暂存区 / 工作区状态；Wrapper 与正式发布流程尚待补齐。
- 正式构建仅面向 `arm64-v8a`；没有 `.so` 的纯 Kotlin / Java APK 不会因 ABI 过滤自动变成只允许 ARM64 安装，须分别验证。
- 已提供手动 `Signed development APK` 工作流，配置四个 Secrets 后生成签名开发版、校验签名 / 包信息 / ABI 并上传 Artifact，不创建正式 Release。配置步骤见 [签名与云端打包](docs/SIGNING.md)。

## 6. GitHub Releases 与版本

- 当前实际构建为 `1.0.0-dev` / `1`，只用于基础功能验证；以下 `1.0.0` 正式流程为待实现契约，不得将开发版作为全功能正式版。
- 正式首版版本名为 `1.0.0`、标签 `v1.0.0`；当前开发版已使用版本码 `1`，正式发布前须递增到更大版本码，版本配置使用唯一来源。
- 每次正式更新同时递增版本名和版本码、维护 CHANGELOG；版本名遵循 SemVer，不复用已发布标签。
- GitHub Actions 校验标签、版本、更新日志、测试与许可，通过后构建签名 ARM64 APK，验证签名 / 包信息 / ABI。
- 先创建草稿 Release，附件和说明完整后再公开；失败时不发布 unsigned / debug 包或空 Release。

每次发布包含：

| 内容 | 约定 |
| --- | --- |
| APK | `app-{version}-arm64-v8a.apk` |
| 校验 | `SHA256SUMS.txt` |
| 更新信息 | 新增、优化、修复、数据迁移 / 兼容说明、已知问题 |
| 对应源码 | 与标签和 APK 对应的完整可构建源码及构建说明 |
| 许可 | GPL 文本、版权与第三方许可，应用内同样可查看 |

正式签名身份长期保持一致，以便覆盖升级；CI 权限最小化，只有发布作业申请 `contents: write`，PR 不接触发布 Secrets。

## 7. 开发与验收顺序

1. 确认全功能清单、日期 / 统计 / 状态机规则，建立工具链、模块、设计 Token 和 CI。
2. 完成公共数据层、纪念日、进度、计数、目标 / 习惯和父子任务。
3. 完成专注、待办、笔记、统计、时间线与完整页面导航。
4. 完成提醒、小组件、备份、显示 / 声音 / 安全、反馈与更新。
5. 完成液态玻璃适配、无障碍、大数据和真机回归，发布 `v1.0.0`。

上述为依赖顺序，不是删减范围。正式发布需要全功能清单逐项验收；仍受第三方接入阻碍的功能必须明确报告，不得标记为已完成。
